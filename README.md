# Smart Plant Monitoring and Watering Advisory System

A full-stack, **software-only** prototype. A Python backend simulates sensor readings, validates and stores them in SQLite, analyses them with an explainable rule engine, raises alerts and serves a React dashboard.

> **All sensor data is simulated.** No hardware is used, and simulated values are labelled as such throughout the UI. Recommendations are advisory, not a guaranteed plant-health assessment.

```
Simulated sensors → validation → ingestion → condition analysis → advisory engine
                  → alert lifecycle → SQLite → dashboard → analytics
```

## Requirements

* Python 3.10+ and Node.js 18+ (with npm). No paid services, no external APIs; works offline after installation.

## Windows setup (PowerShell)

Open two terminals.

**Terminal 1: backend**
```powershell
cd smart-plant-advisor\backend
python -m venv .venv
.venv\Scripts\Activate.ps1          # if blocked: Set-ExecutionPolicy -Scope Process Bypass
pip install -r requirements.txt
python init_db.py                   # optional: the server also initialises the database on start
python run.py                       # http://127.0.0.1:5000
```

**Terminal 2: frontend**
```powershell
cd smart-plant-advisor\frontend
npm install
npm run dev                         # http://localhost:5173
```

Open **http://localhost:5173**. The Vite dev server proxies `/api` to Flask, so no extra configuration is needed.

macOS / Linux: use `source .venv/bin/activate` instead of the Activate script.

## Quick tour

1. **My Plants**: four example profiles (Money Plant, Aloe Vera, Tulsi, Snake Plant) are seeded. Thresholds are editable starting points.
2. **Dashboard** → *Simulate dry soil* (or **Sensor Simulation** → pick a scenario → Start).
3. After a few readings, soil moisture drops below the warning threshold: the dashboard shows *Needs Attention*, **Smart Advisory** explains the rule, and **Alerts** shows an alert that resolves itself when you return to *Normal Conditions*.
4. **History & Analytics** shows charts, min/max/avg, trends, alert and recommendation summaries and a downloadable report.

## Database

SQLite file: `backend/data/plant_advisor.db` (created automatically; git-ignored).

| Table | Purpose |
|---|---|
| `plants` | profiles and thresholds, CHECK constraints on ranges, unique name |
| `sensor_readings` | FK to plant (ON DELETE CASCADE), `source`, `is_simulated`, `scenario`, per-sensor class, health, rule ids; index on (plant_id, recorded_at) |
| `alerts` | FK to plant; partial unique index `(plant_id, alert_type) WHERE status='active'` makes duplicate active alerts impossible |
| `app_settings` | key/value JSON (global settings, active plant) |
| `simulation_state` | persisted scenario and counters |

Timestamps are ISO-8601 UTC (`2026-01-01T10:00:00.000Z`). Foreign keys are on, writes use `BEGIN IMMEDIATE` transactions, WAL mode and a busy timeout. `python init_db.py --reset` deletes and recreates the database.

## How the rules work

Per sensor the thresholds run `critical_low < warning_low ≤ preferred ≤ warning_high < critical_high`. Soil moisture's low warning and temperature's high warning come from the plant profile; humidity and light warn outside the preferred range; critical = warning ± a global margin (Settings). Overall status: any Critical reading, or three or more out-of-range readings → **Critical**; one or two → **Needs Attention**; otherwise **Healthy**. Watering advice depends only on soil moisture, never on a timer. Editing a plant re-evaluates its alerts immediately.

## API

All responses: `{ "data": ... }` on success, `{ "error": { "code", "message", "fields?" } }` on failure (400 bad JSON, 404, 409 conflict/invalid state, 422 validation, 503 database).

| Method | Path | Notes |
|---|---|---|
| GET | `/api/health`, `/api/meta` | health check, scenarios and sensor bounds |
| GET/POST | `/api/plants` | list (with `active_plant_id`) / create |
| GET/PUT/DELETE | `/api/plants/<id>` | delete cascades readings and alerts |
| GET/PUT | `/api/plants/active` | body `{"plant_id": 2}` |
| GET | `/api/plants/<id>/status` | latest reading, classes, health, trends, thresholds, recommendations |
| GET | `/api/plants/<id>/recommendations` | recommendations and thresholds |
| GET | `/api/plants/<id>/readings` | `?range=today\|7d\|30d` or `?from=YYYY-MM-DD&to=…`, `&max_points=` |
| GET | `/api/plants/<id>/readings/latest` | |
| GET | `/api/simulation` | state, scenario, interval, ticks |
| POST | `/api/simulation/start \| pause \| resume \| stop \| reset \| tick` | 409 on invalid transitions; `tick` = one reading (201) |
| PUT | `/api/simulation/scenario` | `{"scenario":"multiple","problems":["dry_soil","low_light"]}` or `{"scenario":"custom","values":{…}}` |
| PUT | `/api/simulation/custom` | `{"values":{"soil_moisture":12,"temperature":24,"humidity":55,"light":55}}` |
| GET | `/api/alerts` | `?plant_id=&severity=&status=&is_read=&range=\|from=&to=` |
| GET | `/api/alerts/summary`, `/api/alerts/<id>` | |
| POST | `/api/alerts/<id>/read \| unread \| resolve`, `/api/alerts/read-all` | |
| GET | `/api/analytics/summary`, `/api/analytics/report` | `?plant_id=` plus the range parameters |
| GET/PUT | `/api/settings` | partial updates, validated atomically |

Example:
```http
PUT /api/simulation/custom
{"values": {"soil_moisture": 500, "temperature": 24, "humidity": 55, "light": 55}}

422 {"error": {"code": "validation_error", "message": "Invalid sensor values.",
      "fields": {"soil_moisture": "Soil Moisture must be between 0 and 100 %."}}}
```
Bounds: soil moisture 0–100 %, temperature −10–60 °C, humidity 0–100 %, light 0–100 (normalized, not lux).

## Troubleshooting

* **"The backend is not reachable"** in the UI: start `python run.py`; check port 5000 is free.
* **Port 5173 in use**: Vite is configured with `strictPort`; stop the other process or change `vite.config.js` (and `ALLOWED_ORIGINS` in `backend/app/config.py`).
* **PowerShell won't activate the venv**: `Set-ExecutionPolicy -Scope Process Bypass`.
* **Charts empty**: no readings exist yet (none are faked); start the simulation or generate one reading.
* **"database is locked"**: only one `run.py` should use the database; the debug reloader is disabled on purpose.
* **Reset everything**: stop the server, run `python init_db.py --reset`.

## Production & Deployment

The application is structured to be deployment-friendly both as a containerized service and on cloud platforms.

### Option 1: Docker / Docker Compose (Recommended)

Run the entire full-stack app (React frontend + Flask backend) with a single command:

```bash
docker compose up --build
```
Then visit **http://localhost:5000**. The multi-stage `Dockerfile` compiles the Vite React app and serves it directly through Flask and Gunicorn with a persistent SQLite data volume.

### Option 2: Cloud Platforms (Render, Railway, Heroku)

* **Render**: Connect the repository and create a new **Web Service** using the included `render.yaml` blueprint, or use the settings:
  * **Build Command**: `cd frontend && npm install && npm run build && cd ../backend && pip install -r requirements.txt`
  * **Start Command**: `cd backend && gunicorn 'app:create_app()' --bind 0.0.0.0:$PORT --workers 1 --threads 4`
* **Heroku / Railway**: The repository includes a `Procfile` configured for Gunicorn with a single worker process (ensuring safe in-memory simulation lifecycle and SQLite WAL concurrency).

### Environment Variables

| Variable | Description | Default |
|---|---|---|
| `PORT` | Listening port for web server | `5000` |
| `HOST` | Interface to bind | `127.0.0.1` locally, `0.0.0.0` in cloud |
| `DB_PATH` | Path to SQLite database file | `backend/data/plant_advisor.db` |
| `ALLOWED_ORIGINS` | Comma-separated list of extra CORS origins | `http://localhost:5173,http://127.0.0.1:5173` |
| `FRONTEND_DIST` | Custom path to frontend `dist` directory | `../frontend/dist` |

## Limitations

* Frontend not browser-tested in the original author build environment (verified syntax and build).
* Simulation state is process-local: a restart stops a running simulation (history and scenario persist).
* Single user, no authentication; the "demo profile" is only a label.
* Thresholds are generic starting points, not horticultural advice.

## Future ESP32 integration

Every reading, from any source, passes through `ingestion.ingest_reading(conn, plant_id, values, source, …)`, which validates, analyses, stores (`source`, `is_simulated`) and runs alerts in one transaction. `esp32` is already a reserved source marked as not simulated. To add hardware: have the device `POST` JSON to a new endpoint (for example `/api/ingest`, with device authentication), which calls `ingest_reading(..., source="esp32")`. Dashboard, analytics and advisory need no changes. Not implemented: that endpoint, device auth, MQTT, cloud.
